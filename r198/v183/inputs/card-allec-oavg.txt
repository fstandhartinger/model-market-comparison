# allec

allec is a fine-tune of [google/gemma-4-31B-it](https://huggingface.co/google/gemma-4-31B-it) that answers multiple-choice
decision questions with a probability for each option. It includes a calibrated last-layer head (`vbll_head.safetensors`,
`vbll_head.json`) whose output is the answer. For ordinary multiple-choice questions that output is the softmax of the option
letters' logits at the answer position, divided by one fitted temperature (T = 1.031); no posterior is involved. For yes / no
questions, a Bayesian last-layer residual on the model's hidden state (a Laplace posterior, integrated over) adjusts the two
logits. (Corrected 2026-10-21: an earlier version of this card described the whole head as Bayesian.)

**Inference engines** (added 2026-10-23). The repository includes these [Decision Index](https://github.com/apolinario/decision-index)
engines; all use the same weights and head:
- `lenavg_bayes_engine:LenAvgBayesEngine` (`lenavg_bayes_engine.py`, with `lenavg_engine.py` and `oavg_engine.py`): length-adaptive
  option-order averaging. For a request whose length L (defined under Usage) is at most 939, every question is also scored with its
  options in other orders, and the results are averaged; longer requests use the single pass. Adds a binary Bayesian correction on averaged yes/no predictions and retains the existing binary posterior on unaveraged yes/no. Ordinary choices use native scores with temperature calibration; their current Bayesian correction controls are zero.
- `lenavg_engine:LenAvgEngine`: the same averaging without the correction on averaged yes / no questions.
- `dikit_engine:DikitEngine`: the single pass of the original release (one forward pass per question).

`config.json` is unchanged. Its `jev_requires_head` block holds training-time labels (for example
`"readout": "posterior_predictive"`); the engines only check that the block is present, and the head's behaviour is as
described above.

Two parts of the model are not optional:
- **Attention.** In the full-attention layers, each prompt's tokens attend to every token of the same prompt; the sliding-window
  layers stay causal (window 1,024). transformers' stock attention would run the full-attention layers causally and give different
  answers, so the model is served with the `jev_mem` attention function in `fullft_mem.py`. It registers with transformers'
  attention interface and runs on PyTorch SDPA (memory-efficient and flash kernels). The engine refuses any other attention.
- **The head.** The letter logits on their own are not the model's answer.

The weights (`model-*.safetensors`, `vbll_head.safetensors`) are hosted here on the Hugging Face Hub; the GitHub mirror,
[treewaterer/allec](https://github.com/treewaterer/allec), holds the code and this card only.

## Usage

The engines are `lenavg_bayes_engine.py`, `lenavg_engine.py` and `oavg_engine.py` on top of the single-pass engine `dikit_engine.py`, with `garas_vbll_engine.py`, `vbll_core.py`,
`fullft_mem.py`, `garas_engine.py` and `garas_core.py`. They need the Decision Index kit:

```bash
pip install "git+https://github.com/apolinario/decision-index@9eb2dbe2a358004c8782c66e40a83ac07b953fec"
REPO=$(python -c "from huggingface_hub import snapshot_download; print(snapshot_download('plantwaterer/allec'))")
PYTHONPATH="$REPO" python -m decision_index run --engine lenavg_bayes_engine:LenAvgBayesEngine --option model="$REPO" --compact --out runs/allec-oavg
```

For the single pass of the original release, use `--engine dikit_engine:DikitEngine` instead.

In Python:

```python
import sys
from huggingface_hub import snapshot_download

repo = snapshot_download("plantwaterer/allec")
sys.path.insert(0, repo)
from lenavg_bayes_engine import LenAvgBayesEngine          # needs the decision_index kit installed

engine = LenAvgBayesEngine(model=repo)               # bf16 on "cuda"; the head runs on the CPU
response, _ = engine(
    "The forecast gives a 70% chance of heavy rain this afternoon. The match is outdoors, on grass.",
    {"plan": {"type": "choice", "instructions": "What should the organisers do?",
              "criteria": {"play": "Play as planned", "indoors": "Move it indoors", "postpone": "Postpone it"}},
     "rain": {"type": "noul", "instructions": "Is heavy rain likely?"}})
print(response["answers"])
```

The inference procedure is as follows:
- **Prompts:** one prompt per question, with the model's chat template and the options lettered A-Z a-z. A choice question's
  options are shown in one fixed non-identity order derived from a hash of the request. Yes / no questions use the options `Yes`
  and `No`; when the request gives their definitions (its `criteria`), they are shown as `Yes: <definition>` / `No: <definition>`.
- **Read-out:** one forward pass per prompt. The final hidden state and the option letters' logits (fp32, with the model's logit
  soft-cap) go through the head, on the CPU in float64, which gives the probabilities.
- **Order averaging** (`lenavg_bayes_engine:LenAvgBayesEngine`):
  - *Which requests:* L = the sum over the request's questions of [len(state) + len(instructions) + the sum over the question's
    criteria of (len(str(key)) + len(str(value)))], with Python's `len()`. A string state counts its characters; a dictionary state
    counts its top-level keys, not its text; a missing state counts 0. The state is counted once per question. A request is averaged
    if and only if L <= 939; otherwise every question takes the single pass described above.
  - *Choice questions with up to 52 options:* scored in 4 option orders, the engine's own order and 3 re-letterings
    `numpy.random.default_rng(20261021 + 1000 * j + K).permutation(K)` for j = 1, 2, 3 (K options). For each order the head's output
    (the softmax of the letters' logits divided by T = 1.031) is mapped back to the options; the 4 vectors are averaged with equal
    weight, then raised to the power 1 / 0.95438 and renormalised.
  - *Yes / no:* the native letter softmax of the base order and of the swapped order (`No` first), averaged, then raised to the
    power 1 / 0.93738 and renormalised (p). Then the binary Bayesian correction: the head's yes / no readout is computed from the base
    prompt's hidden state and the log of the averaged native probabilities, once with its fitted residual and posterior variance and
    once with both switched off (beta = 0, infl = 0); the difference of the two log-odds is added to the log-odds of p. No extra
    temperature.
  - *More than 52 options:* the single pass.
  - The re-lettered prompts of a request are packed into the same forward passes as its other prompts.
- **Batching:** the prompts of one request run in packed rows of up to 32,768 tokens, each prompt with its own positions, so a
  prompt only attends to itself.
- **More than 52 options:** handled in two rounds.
- **No truncation:** a request that does not fit 32,768 tokens is reported as unsupported.

Requirements: one GPU with at least 75 GB (the bf16 weights are 62 GB). Tested on 1 x H100 80GB and 1 x RTX PRO 6000 (96 GB) with
torch 2.14.1 (CUDA 13.0), transformers 5.12.1, huggingface_hub, safetensors and numpy. bf16 results differ slightly between GPU types.

## Evaluation

**Decision Index 0.3, public panel (37 benchmarks), with order averaging (`lenavg_bayes_engine:LenAvgBayesEngine`).** The run used this repository's
weights, head and engines, with the kit's runner and scorer at commit 9eb2dbe2, in bf16. The full public suite ran as 8 row shards on
single H100 80GB GPUs, merged without changes. This is our own run of the public kit, not a leaderboard entry. The run files are at
[plantwaterer/allec-oavg-decision-index](https://huggingface.co/datasets/plantwaterer/allec-oavg-decision-index). 94,198 of the 140,620 requests (67%) were averaged.

Nothing was truncated. The listed trained-on test item was answered wrong, so the two rows are equal. That is +0.43 points over the single pass (61.60, below). Against the same averaging without the yes / no correction
(`lenavg_engine:LenAvgEngine`, 62.04 on the same suite), the difference is -0.007 points (95% CI -0.034 to +0.017: a paired
bootstrap over the suite's test items with the board's own metrics; it does not cover variation between training runs). The
correction changes only the 2,700 averaged yes / no requests (all RAGTruth); its effect there is small (median |change| 0.004 in
probability).

### Overlap with evaluation data

No test split of any benchmark was used. The head's fit and calibration data include train-split rows of CLINC150, GSM8K,
Amazon ESCI, BANKING77 and WinoGrande; the training data include Lichess puzzles (a different dataset from ChessBench's).

An audit of the training text, the head's data included, against the Decision Index public suite found 1 test item that is an
exact or near-exact duplicate of a CLINC150 train-split utterance in the head's fit data: `5:CLINC150+OOS:CLINC150+OOS:test:1591`.
It is counted as wrong in the board-rule numbers above, as the board does for train-split duplicates of test items (see the
Contamination section of the [Decision Index methodology](https://multimodalart-jev-decision-index.static.hf.space/methodology.html)).
