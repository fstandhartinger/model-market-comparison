### CR-167.4 / CR-168.1 — legacy beacon silently dropped

The deployed banner route's local `HOSTS` set lists only `benchmarkheaven.com` and `www`, but the
shared `PUBLIC_HOSTS`/`publicOrigin` guard also includes the legacy Mintapis host. Consequently, a
legacy browser beacon receives HTTP 204 while no event is forwarded to Umami. The endpoint response
alone had been treated as proof in prior records; it is not proof of forwarding. This is an analytics
accuracy defect, with no change to the consent basis or payload.

This branch removes the narrower duplicate allowlist and relies on the shared `publicOrigin` guard.
A route-level integration check failed before the change (two of three configured hosts forwarded)
and passed after it (all three forwarded, mismatched/unlisted host refused). The retained receipt
`banner-route-integration.json` runs the route in-process with the Umami fetch mocked, so it proves
the route's forwarding decision without sending any analytics traffic. The checked-in regression
test verifies `publicOrigin`'s configured-host behavior and the route's use of the shared guard.
Because this fix is not deployed, CR-167.4, CR-168.1, and CR-174.1 remain open pending live proof.
