## The defect this gate found: the grid head named nobody once you scrolled

`/jev-models` ships the per-task grid (`CR-90.2`, F-140) as a dense heatmap: 231 task rows × 21 system columns inside
a `max-h-[38rem] overflow-auto` box, with the system names rotated in the head. Measured on the live page before the
fix, at 390 px and at 1440 px:

| what | measured |
|---|---|
| `getComputedStyle(thead th).position` | `static` |
| scroll height of the grid box | 7,250 px (390 px) / 7,241 px (1440 px) |
| head position after scrolling to the bottom | **6,185 px above the scrollport** (390) / 6,100 px (1440) |

So from roughly row 20 onward — on desktop as much as on a phone — every ✓ / × / ! cell belonged to an unnamed
column. The only thing still naming them was each cell's native `title`, which is hover-only and never opens on
touch: the same failure mode the last gate filed against F-140's `topic · type` title, one element higher up.

The markup had already declared the intent. The Task cells carry `bh-jev-sticky` — but that class is defined only
under `.bh-jev-table` (`app/globals.css:436`), and this grid is a `.bh-table` (`components/JevModelsV12.tsx:294`), so
the class resolved to **nothing at all**. A class named `sticky` on a table that does not scroll-lock anything is
exactly the kind of statement this loop keeps finding: the code says one thing, the page does another.

**Fixed** in `app/globals.css`: `[data-bh-jev12-task-table] thead th { position: sticky; top: 0; z-index: 2; }`. The
head already carries an opaque background from `.bh-table thead th`, so nothing shows through it. Proven against the
live page by injecting the rule before committing it: head `sticky`, pinned at **offset 1 px** in the scrollport
after scrolling all 231 rows, in both themes at 390 and 1440 — and **byte-identical at scroll-top** (head 162 px,
first row top unchanged, no page overflow), so Fable's pass-25 shots still describe the page.

Pinned so it cannot come back: one live check per context in `verify-cr-90.mjs` (the head is `sticky`, still inside
the scrollport after a full scroll, and the box really does scroll) and an offline pin of the CSS rule and its hook
in `test/jevbench-v12-scope-labels.test.mjs`.

### Filed, not fixed: the Task column is still not pinned horizontally

The other half of the dead `bh-jev-sticky` is a design question and is left to the design authority rather than
guessed at here. At 390 px the grid scrolls horizontally inside a 324 px box (table `min-w-[54rem]`), and the Task
cell needs **291 px** of it for the id plus its type tag (**451 px** at 1.3× text). Pinning it as-is would leave
one outcome cell visible; capping it at the main table's phone width (170 px) would clip the type tag that
iteration 131 just made visible. Either the id gets a phone-length form or the pin stays off — a Fable call. Today,
scrolling right on a phone loses the row label (measured: the Task cell sits at `left: −366 px` after a 400 px
scroll).

## The AA shrink guard (iteration 133), re-read

The guard itself is sound and the claim behind it checks out. Re-derived from the committed evidence: the two
captured bodies (`gpt-5-6-sol`, `claude-sonnet-5`, sha256 in `live-manifest.jsonl`) and the row diff — 156 → 145
rows is **12 retired identities and one new `step-5`**, 156 − 12 + 1 = 145, with a scored denominator of 644. The
`previous`-count guard is not weakened: `parseAaEfficiency`'s `previous` only raises `minimum` above
`AA_EFFICIENCY_MIN_ROWS`, and the live path re-implements exactly that comparison before the confirmation runs. The
framing in the code comment is honest about what a second model page can and cannot prove — both pages come from the
same build, so this separates a partial render from a real population change, and nothing more.

Two things were wrong in the surrounding control flow, and this gate fixed both:

- **The wrong page was written.** On a confirmed shrink the collector did `response = firstSuccessful.body` — the
  first page that ever parsed. That is a *different* page than the `candidate` whose rows the confirmation loop
  compared, as soon as an earlier slug was rejected: its rows were never compared with anything. Now it writes
  `body` / `url`, the page that was actually confirmed, and `firstSuccessful` is gone rather than left as dead
  state.
- **An unconfirmed shrink was reported as a failed probe.** The `AA efficiency shrink not independently confirmed`
  throw was swallowed by the per-slug `catch`, so the loop moved to the next slug and re-fetched the pages the
  confirmation had just read (up to 6 requests for 3 slugs), finishing with
  `AA efficiency: every model-page probe failed`. It failed closed — but a scheduled run has to be diagnosed from
  its receipt, and the receipt named the wrong cause. The rethrow guard now covers both `AA efficiency shrink`
  messages, so the decision surfaces as itself and each page is read at most once. A test pins that: confirming
  pages unreachable → rejects with `shrink not independently confirmed`, exactly `AA_EFFICIENCY_MODEL_SLUGS.length`
  requests, snapshot untouched.

`CR-85.1` stays **open** and this gate agrees with iteration 133's own reading: the fix is the guard, not a
published digest. `data/raw/aa-efficiency.json` in the repo is still the **156**-row snapshot of 2026-09-18 — the
live refresh ran against a temp target — and the first real scheduled digest still has no successful publication
receipt. The next 05:17 run is the evidence that row is waiting for.
