# CR-67.5 — Consent decision for the visitor statistics (decision record)

Status: **decided by the implementer (iteration 95, claude-opus), independent review required before deploy.**
Not legal advice. Full source research with verbatim quotes: `/opt/benchmarkheaven/state/ux-evidence/iter94-cr67/CR-67.5-consent-decision-draft.md`
(iteration 94). This record binds that research to the code that is actually shipped.

## 1. What is implemented (the facts the decision rests on)

Code: `lib/visit-stats.mjs` (classification, aggregation, schema, report), `lib/visit-counter.ts` (Node process
memory + flush), `middleware.ts` (calls the counter for non-API requests), `app/api/operator/visits/route.ts`
(operator report). Tests: `test/visit-stats.test.mjs`.

| Question | Answer from the code |
|---|---|
| Storage on / reading from the device | **None.** No cookie, `localStorage`, `sessionStorage`, script, pixel, beacon, `Accept-CH`/client hint, ETag or link decoration. The counter runs only on the server, inside the request the browser already makes for the page. |
| Data used per request (in memory, then discarded) | Method, URL path, `Sec-Fetch-Dest`/`Accept`/`Sec-Purpose` headers (is it a full page load, not a prefetch?), `User-Agent` (bot filter only), `Referer` (host only), `Sec-GPC`/`DNT` (objection). **The IP address is never read.** |
| Identifiers | **None.** No IP, no hash, no salt, no fingerprint, no session or account link. Consequence: unique visitors are **not** measured. |
| What is stored | Table `bh_visit_daily(day, path, referrer_host, views, visits)` — daily totals only. `path` has no query string and is limited to known routes (other paths fold into `(other)`); `referrer_host` is a host name without path or query, empty for direct/same-site. "views" = full page loads (in-app navigations are not visible to the middleware and are not counted); "visits" = page loads without a same-site referrer. |
| Where | The existing first-party Postgres (`benchmarkheaven_accounts`) on the Hetzner server in the EU, in its own table; never joined with `bh_users`. No third party, no analytics vendor, no transfer outside the EU. |
| Retention | Each flush deletes rows older than 13 months. In-memory totals exist for at most ~60 s before being written. |
| Output | `GET /api/operator/visits?days=N` (Bearer `VISIT_STATS_TOKEN`, same-origin, `no-store`): daily totals, top 25 pages, top 25 referrer hosts. No visitor-level data exists that could be exported. |
| Objection | Requests with `Sec-GPC: 1` or `DNT: 1` are not counted; objection by email is also offered. |

## 2. Decision

**(a) No consent is required under § 25 TDDDG, and no banner is added (CR-67.6: no-banner branch).**

- § 25(1) TDDDG covers *storing information on* or *accessing information stored in* the terminal equipment. The
  counter does neither: it only processes header data the browser sends for every page request. LfDI
  Baden-Württemberg (FAQ Cookies und Tracking, A.3.1) states that IP address and User-Agent sent automatically are not
  an "access" under § 25 and names local log analysis without third parties, data-minimal configuration and no
  merging of usage data as the model for consent-free reach measurement — this implementation is stricter (no IP at
  all, no log rows).
- DSK *OH Digitale Dienste* v1.2 (Nov 2024) no longer repeats the 2021/22 header-data sentence, but keeps active
  reading via JavaScript and server-side fingerprint hashes (Rn. 23–24) as access; neither happens here. Rn. 88 names
  "bei jedem Abruf einer Seite den Zähler für diese Seite um Eins zu erhöhen" as the plain counting case.
- EDPB Guidelines 2/2023 v2.0 (paras. 43, 54–55) bring header/IP-based **tracking and fingerprinting** into Art. 5(3)
  ePD. No identifier is derived and no visitor is recognised or tracked, so even that broader reading does not reach a
  per-page counter without an identifier. This is why the daily IP+UA hash for unique visitors (draft "variant A")
  was **not** built.
- GDPR: the persisted daily totals relate to no identifiable person. The transient processing of the request
  headers is based on Art. 6(1)(f) (own reach and capacity insight; no profile, no third party, reasonable
  expectation), with Art. 13 information on `/privacy#visitor-statistics` and an Art. 21 objection route.

**Existing browser storage (outside the counter, checked for completeness):** `bh-theme`, the filter/settings store,
saved presets, `bh.valueMap.v1`, shortlist selection, dismissed-hint flags and a sign-in toast flag in
`sessionStorage`; while signed in, the Auth.js session and CSRF cookies. All hold state the visitor set or needs for
the function they use, never leave the browser except the explicit account sync, and are disclosed on `/privacy` —
§ 25(2) Nr. 2 TDDDG. None of them is read by the counter.

## 3. Conditions that would reopen this decision

Adding any of the following makes the statistics consent-relevant or needs a new record: client-side script/beacon,
cookie or storage for statistics, any IP-derived or hashed key (unique visitors), `Accept-CH`, full referrer URLs or
query strings, an external analytics provider, joining statistics with accounts, longer retention.

## 4. Technical proof (for the verifier)

1. `node --test test/visit-stats.test.mjs` — classification, no-identifier schema, retention delete, aggregate-only
   report, no client analytics in the layout.
2. Live: load pages at 1440 and 390 px; the browser context has **no cookies and no storage keys** beyond the
   existing functional ones listed above, and **no request to any third-party analytics host**; the response carries no
   `Set-Cookie` for anonymous page loads.
3. Live: `/api/operator/visits` without the token → 401 (404 when unconfigured); with the token → aggregate JSON only.
