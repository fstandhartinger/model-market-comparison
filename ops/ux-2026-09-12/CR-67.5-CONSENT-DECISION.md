# CR-67.5 — Consent decision for the visitor statistics (decision record)

Status: **decided by the implementer (iteration 95, claude-opus); independent review by Codex (round 1 FAIL → fixed, see §5).**
Not legal advice. Full source research with verbatim quotes: `/opt/benchmarkheaven/state/ux-evidence/iter94-cr67/CR-67.5-consent-decision-draft.md`
(iteration 94). This record binds that research to the code that is actually shipped.

## 1. What is implemented (the facts the decision rests on)

Code: `lib/visit-stats.mjs` (classification, aggregation, schema, report), `lib/visit-counter.ts` (Node process
memory + flush), `middleware.ts` (calls the counter for non-API requests), `app/api/operator/visits/route.ts`
(operator report). Tests: `test/visit-stats.test.mjs`.

| Question | Answer from the code |
|---|---|
| Storage on / active reading from the device | **None by the counter.** No cookie, `localStorage`, `sessionStorage`, script, pixel, beacon, extra request, `Accept-CH`/client hint, ETag or link decoration. The counter runs only on the server, on the request the browser already makes for the page. (The site's separate functional storage is listed in §2.) |
| Data used per request (in memory, then discarded) | Method, URL path, `Sec-Fetch-Dest`/`Accept`/`Sec-Purpose`/`Purpose` (full page load, not a prefetch or file?), the full `User-Agent` string (regex bot filter only, never stored), `Referer` (reduced to the host), `Sec-GPC`/`DNT` (objection). Several of these headers are optional and not sent with every request. **The IP address and forwarded-IP headers are never read.** |
| Identifiers | **None.** No IP, no hash, no salt, no fingerprint, no session or account link. Consequence: unique visitors are **not** measured. |
| What is stored | Table `bh_visit_daily(day, path, referrer_host, views, visits)` — daily totals only. `path` has no query string and is limited to known routes (other paths are stored as one `(unknown route)` row); `referrer_host` is a host name without path or query, empty for direct/same-site. "views" = full page loads (in-app navigations are not visible to the middleware and are not counted); "visits" = page loads without a same-site referrer. |
| Where | The existing first-party Postgres `benchmarkheaven_accounts`, in its own table; never joined with `bh_users`. The code accepts any `ACCOUNTS_DATABASE_URL`, so the location is a **deployment fact, proven by evidence, not by code**: that database runs on the Sandy server (65.109.49.103, AS24940 Hetzner Online GmbH, Helsinki, Finland — the same host that serves benchmarkheaven.com), and the live verification checks that page loads sent to benchmarkheaven.com arrive as rows in that server's local Postgres (`/opt/benchmarkheaven/state/ux-evidence/iter95-cr67/deployment-location.txt`). No analytics vendor; the counter has no other integration. Hetzner is the hosting processor. |
| Retention | A separate delete of rows older than 13 months runs at least hourly while the server runs (timer started when the counter module is loaded in a configured server process, and on the first counted request; independent of traffic). Unwritten totals are normally written within ~60 s; if the database is unreachable they are kept in memory for at most the current and previous UTC day, then dropped. At most 5,000 distinct rows are held in memory; further new rows are skipped, also when a failed write is put back. |
| Output | `GET /api/operator/visits?days=N` (Bearer `VISIT_STATS_TOKEN` compared in constant time; 404 when unconfigured; no CORS header; `no-store`): daily totals; the top 25 pages and top 25 referrer hosts that have at least 3 page loads in the period; and one "(other)" row each that combines all remaining rows (below 3, or beyond the top 25), so the report does not name a page or referrer with a single visit. The database itself holds exact daily rows (reachable only with the database credential). |
| Objection | Requests with `Sec-GPC: 1` or `DNT: 1` are not counted. Email objection is offered; because totals cannot be traced to a person, it is answered with an explanation and the GPC/DNT route rather than a per-person deletion (stated as such on `/privacy`). |

## 2. Decision

**(a) No consent is required under § 25 TDDDG, and no banner is added (CR-67.6: no-banner branch).**

- § 25(1) TDDDG covers *storing information on* or *accessing information stored in* the terminal equipment. The
  counter stores nothing and runs nothing on the device; it only evaluates HTTP headers of the page request the
  visitor makes. LfDI
  Baden-Württemberg (FAQ Cookies und Tracking, A.3.1) states that IP address and User-Agent sent automatically are not
  an "access" under § 25 and names local log analysis without third parties, data-minimal configuration and no
  merging of usage data as the model for consent-free reach measurement — this implementation is stricter (no IP at
  all, no log rows).
- DSK *OH Digitale Dienste* v1.2 (Nov 2024) no longer repeats the 2021/22 header-data sentence, but keeps active
  reading via JavaScript and server-side fingerprint hashes (Rn. 23–24) as access; neither happens here. Rn. 88 names
  "bei jedem Abruf einer Seite den Zähler für diese Seite um Eins zu erhöhen" as the plain counting case.
- EDPB Guidelines 2/2023 v2.0 (paras. 43, 54–55) bring header/IP-based **tracking and fingerprinting** into Art. 5(3)
  ePD. No identifier is derived and no visitor is recognised or tracked, which puts this counter well outside those
  examples. This is why the daily IP+UA hash for unique visitors (draft "variant A") was **not** built.
- **Residual uncertainty (stated, not hidden):** the EDPB reading of "access" is broad and DSK v1.2 Rn. 89–90 says
  reach measurement must be judged per configuration and is "nicht per se" part of the base service. The decision is
  therefore our documented assessment for exactly this configuration, and `/privacy` words it as "in our assessment".
  If a supervisory authority or court treats header evaluation as access requiring consent, the fallback is to switch
  the counter off (remove the middleware call), not to add a banner.
- GDPR: the persisted daily totals relate to no identifiable person. The transient processing of the request
  headers is based on Art. 6(1)(f) (own reach and capacity insight; no profile, no third party, reasonable
  expectation), with Art. 13 information on `/privacy#visitor-statistics` and an Art. 21 objection route.

**Existing browser storage (outside the counter, checked for completeness):** `bh-theme`, the filter/settings store,
saved presets, `bh.valueMap.v1`, shortlist selection, dismissed-hint flags and a sign-in toast flag in
`sessionStorage`; while signed in, the Auth.js session and CSRF cookies. All hold state the visitor set or needs for
the function they use, never leave the browser except the explicit account sync, and are disclosed on `/privacy` —
§ 25(2) Nr. 2 TDDDG. None of them is read by the counter.

## 3. Conditions that would reopen this decision

Adding any of the following makes the statistics consent-relevant or needs a new record: client-side script/beacon,
cookie or storage for statistics, any IP-derived or hashed key (unique visitors), `Accept-CH`, full referrer URLs or
query strings, an external analytics provider, joining statistics with accounts, longer retention.

## 6. Reopened 2026-09-25 — the fast-lane banner's interaction counts (D208)

Status: **decided by iteration 230 (claude-opus), the engine that did *not* write the banner. Needs an
independent reviewer, like §5. Not legal advice.** Raised by review gate `REVIEW-20260925T192004Z.md`,
which found that CR-167 shipped a `navigator.sendBeacon` call while §3 above names "client-side
script/beacon" and "an external analytics provider" as conditions that reopen this record — and that the
record was never revisited. Only the *name* of the test carrying its premise was rewritten. That gap is
real and this section closes it. §§1–5 describe the middleware page counter and are unchanged; this

### 6.1 What was added (the facts this decision rests on)

Code: `components/FastlaneBanner.tsx` (the beacon), `app/api/fastlane-banner-event/route.ts` (the
first-party endpoint), `/privacy` (disclosure). Three events: `fastlane_banner_view`,
`fastlane_banner_click`, `fastlane_banner_dismiss`, on `/jev-models` and `/image-jev-bench` only.

| Question | Answer from the code |
|---|---|
| Storage on / active reading from the device **for statistics** | **None.** `sendBeacon` is an outgoing POST. Its body is built from the event name and which of the two page groups the visitor is on — both already known to the server from the request it just answered. No cookie is set, no `localStorage`/`sessionStorage`/cache/client hint is read for it, and the endpoint never reads a cookie. |
| Device storage **for function** | The dismissal choice: `localStorage["bh-fastlane-banner-hidden"]` for "Don't show again", `sessionStorage["bh-fastlane-banner-closed"]` for ×, both in `try/catch`. This is state the visitor themselves set by pressing the control, it never leaves the browser, and it is not read by the statistics path — it only decides whether the banner renders. § 25(2) Nr. 2 TDDDG, same footing as `bh-theme` in §2. Disclosed on `/privacy`. |
| Payload | `{ name, page }` where `name` is one of the three allow-listed event names and `page` is literally `"jev-models"` or `"image-jev-bench"`. No URL, no query string, no referrer, no form data, no identifier. The endpoint rejects anything else. |
| Identifiers | **None derived.** No IP, no hash, no salt, no fingerprint, no visitor or session key. Unique visitors are still not measured. |
| Recipient | Our **self-hosted Umami**, `bh-analytics.app.mintapis.com`. It resolves to **65.109.49.103** — the same Sandy/Hetzner host that serves benchmarkheaven.com (checked 2026-09-25). **The browser never contacts it:** the beacon goes to our own `/api/...` route and the site's server forwards it, so the forward is server-to-server on the same machine. There is no analytics vendor and no new processor beyond Hetzner as host. `grep` over `app/`, `components/`, `lib/` and `middleware.ts` finds no Umami script or pixel in any page: the site still ships **no client-side analytics script**, which is what `test/visit-stats.test.mjs` asserts. |
| What Umami receives | `type: "event"`, our website id, the hostname, a fixed `url` of `/jev-models` or `/image-jev-bench`, and the event name — plus the visitor's **User-Agent**, forwarded by our server. The visitor's **IP is not forwarded**; Umami sees our own server as the client. |
| Objection | `DNT: 1` / `Sec-GPC: 1` stop the event on **both** sides: the client does not send it and the endpoint drops it. |
| Hardening | `Origin` must equal the ingress-provided public origin and its host must be `benchmarkheaven.com` or `www.benchmarkheaven.com`; `content-type` must be JSON; the body is capped at 256 bytes while reading, not just by the header; the Umami origin is pinned with `redirect: "error"` and a 4 s timeout; every path answers `204` so analytics can never interrupt navigation or a dismissal. |

### 6.2 The §3 conditions, one by one

- **"client-side script/beacon … for statistics" — met literally.** This is why the record is reopened
  rather than carried over. But the reason the condition exists — a beacon normally implies storing in or
  reading from the terminal equipment — does not materialise: nothing is stored and nothing is read. Under
  § 25(1) TDDDG the relevant act is storage or access, not the existence of an outgoing request; DSK
  *OH Digitale Dienste* v1.2 Rn. 23–24 names active reading via JavaScript and server-side fingerprint
  hashes as access, and neither happens. Sending data the server already has is not access to the device.
- **"an external analytics provider" — not met in substance.** Umami is our own instance on our own host,
  reached only by our own server. No visitor data leaves the Hetzner machine that already serves the page.
  Had the browser been pointed at a vendor's script, the answer here would be the opposite.
- **"any IP-derived or hashed key (unique visitors)" — not met.** The visitor's IP is never forwarded, so
  Umami's own visitor hash is computed over *our server's* address, identical for everyone. No visitor is
  recognised across events or pages. See the residual in §6.4 about the User-Agent.
- **"cookie or storage for statistics" — not met.** The only new storage is the dismissal choice, which is
  functional (above).
- **"full referrer URLs or query strings" — not met.** The forwarded `url` is one of two fixed strings from
  an allow-list; nothing from the address bar reaches it.
- **"joining statistics with accounts" — not met.** A same-origin `sendBeacon` from a signed-in visitor will
  carry the Auth.js session cookie, as any same-origin POST does. The endpoint **never reads a cookie**, has
  no database access and no account code path, and forwards only `{name, page}`. Nothing is joined.
- **"longer retention" — open, see §6.4.** Retention of the middleware counter (13 months) is unchanged.

### 6.3 Decision

**No consent is required for these three counts under § 25 TDDDG, and the no-banner branch of CR-67.6
still stands.** The banner's device storage is the visitor's own dismissal choice under § 25(2) Nr. 2.
Under the GDPR the counts relate to no identifiable person; the transient processing rests on Art. 6(1)(f)
(does the paid-evaluation offer reach anyone at all — no profile, no third party, no vendor), with Art. 13
information already published in the "priority-evaluation banner" paragraph on `/privacy` and the same
Art. 21 objection route as §1, plus GPC/DNT honoured on both sides.

Stated plainly: this is a **second** statistics mechanism next to the middleware counter, and it is the
first one that runs code in the visitor's browser. That is a change in kind, even though the data is
narrower than what the page counter already collects. It is recorded as such rather than folded into §2.

### 6.4 Residual uncertainty and open items (stated, not hidden)

1. **The forwarded User-Agent is the only visitor-derived field, and the three counters do not need it.**
   With a constant server IP it is the sole varying input to Umami's visitor hash, so a rare User-Agent
   could in principle be distinctive within a day. Nothing in this system tries to use that, and `/privacy`
   discloses the forward. The one-line minimisation — send a fixed User-Agent — is available and would cost
   only Umami's browser/OS breakdown, which nobody asked for. **Not changed here**, because it is shipped
   behaviour of another job's CR; flagged for Florian or the next review to decide.
2. **Umami's own retention on our instance is not stated in this repository.** The 13-month deletion in §1
   covers `bh_visit_daily`, not the Umami event store. Whoever owns `bh-analytics.app.mintapis.com` should
   record its retention here; until then this record cannot claim a retention period for the events.
3. **The endpoint is unauthenticated.** `Origin` is a browser convention, so a non-browser client can post
   the three allow-listed event names and inflate the counters. That is an **accuracy** problem, not a
   privacy one — the payload is a fixed enum either way — and it is inherent to any public beacon. Treat
   the three numbers as a floor-quality signal, never as a measurement.
4. The §2 caveat still applies: if a supervisory authority or court treats this as access requiring consent,
   the fallback is to switch the mechanism off (remove the beacon), not to add a banner.

**Conditions that would reopen §6:** pointing the browser at any host other than our own origin; a
third-party or off-host analytics service; forwarding the IP or any hash of it; any per-visitor or
per-session key; reading a cookie, storage or client hint in the beacon path; adding event names or payload
fields beyond the fixed enum; or joining these events with accounts or with `bh_visit_daily`.
