  encrypted-handover message; the age recipient is shown. **Production is in TEST mode and this

  *validation* error rather than the 503 an unconfigured mode/key would give — so mode is `test`

  evaluation requests" sections covering the processed fields, the GDPR basis, EU-hosted Postgres,

- **CR-140.3 — in-progress. Two defects found by this gate; not fixed here, and deliberately so.**
  The verified half is substantial: `verifyStripeSignature` is a correct
  `HMAC-SHA256(t.payload)` with a `whsec_` prefix check, a 300 s tolerance and `timingSafeEqual`;
  the webhook binds `livemode` to the configured mode, requires `client_reference_id` *and*
  `metadata.priority_request_id` to equal the request, requires `amount_subtotal` to equal the
  stored `base_amount`, takes `FOR UPDATE`, and de-duplicates on a unique `event_id` — replays and
  retries are safe. Both routes log only a truncated error message. The two defects:
  1. **Unbounded notification retry loop.** `main()`'s `while process_notification(): pass` drains
     rows, but a row whose `notify_florian()` exits non-zero is written back to
     `notification_status='pending'` — exactly what `claim_notification()` selects. The same row is
     re-claimed immediately, in the same cycle, until `TimeoutStartSec=180` kills the unit, every
     five minutes. `notification_attempts` is incremented but never read.
  2. **Uncapped automatic refund retry, one Telegram notice per attempt.** A non-retryable Stripe
     error sets `refund_due`/`refund_status='failed'` and clears the idempotency key; the automatic
     clause `status='refund_due' AND updated_at <= now()-interval '5 minutes'` re-claims it with a
     *new* key, and `process_due_refunds()` notifies on every `failed`/`unknown`/`error`. A
     permanently unrefundable payment therefore notifies Florian every five minutes indefinitely.
     `refund_attempts` is incremented but never compared.

  Neither can fire today: the table holds only terminal rows (2 `refunded`, 1 `expired`, all
  `test`), and `jevbench-priority-worker.timer` is active and exiting 0. This gate did **not**
  patch them — `ops/priority-evaluation/*` and its `~/bin/` mirror are owned by a job that is
  still running, and a gate-written edit to a live refund worker would diverge the repo from the
  deployed copy. Reported with suggested minimal fixes to agent-board thread #8, entry **#731**.
- **CR-140.5 — in-progress.** What this gate could verify independently, it did: production is in
